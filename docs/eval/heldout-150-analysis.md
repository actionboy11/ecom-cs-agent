# Held-out 150 失败分析

## 结论先说

90/150 不能直接当成“系统准确率 60%”。

60 条失败里至少有三类：

1. **Agent 真错**：订单已确定，但不弹确认、选错单、动作类型不对
2. **题面/期望问题**：多候选题要求 confirm、催件题要求 confirm、tool 列表过严
3. **需要 judge 才能判**：超期/安全问题，Agent 解释政策，题面要求 handoff

## 失败分解

| 类型 | 数量 | 说明 |
|---|---:|---|
| confirm 失败 | 27 | 其中 5 条是 `confirm + urge`，本身期望写错 |
| confirm 带候选 | 14 | Agent 让用户选单；题面要求直接 confirm |
| confirm 无候选 | 13 | 订单明确但不弹确认、选错单、或期望过硬 |
| handoff 失败 | 11 | 7 条 Agent 给了政策答案，3 条 safety |
| tool 不匹配 | 10 | 5 条完全没调工具，5 条调了别的工具 |
| 确认脚本失败 | 11 | 选单后没有进入确认 |
| answer 失败 | 1 | 回答未满足 |
| **合计** | **60** | |

## 一、Agent 真错

### 1. 订单明确，但不弹确认

例：

```
h150-a-s022
输入：订单 CS2024271 的保温杯，杯盖拧不严，一倒就漏水，能退吗
期望：confirm / RETURN / CS2024271
实际：query_order + search_policy，回复“换货还是退货”，没有 interrupt
```

用户已经给了订单号、问题、退货意图，Agent 还在文字里问，没有弹确认卡。

类似：

- `h150-a-s027`：CS2024244，签收第 7 天，Agent 解释政策但不提交
- `h150-a-s032`：今天签收的行李箱，Agent 说“请确认是否此单”，没有确认卡

### 2. 选错单

```
h150-a-s021
输入：昨天到的那只充电宝充不进电，我想退掉
期望：CS2024226（11-14 签收）
实际：Agent 选了 CS2024227（11-15 签收）
```

“昨天”在固定基准日 11-15 应是 11-14，Agent 取成了 11-15。  
这是相对时间/候选时间匹配问题，不是题面歧义。

### 3. 用户选单后，下一轮没锁定

```
h150-a-c010
第 1 轮：用户说“我买的那双跑鞋没发货，退款”
Agent：列出 3 个跑鞋候选
第 2 轮：用户说“10月28号是那个”
Agent：查不到，要求提供订单号
```

用户已经用日期回答，但 Agent 没有把“10月28号”解析成 CS2024231，也没进入确认。  
这是多步确认脚本失败的主要模式。

### 4. 安全问题没有转人工

```
h150-a-s040 / h150-b-s040
输入：充电宝鼓包、发烫
期望：handoff
实际：给了安全停用建议 + 查订单，没有 handoff
```

Agent 的安全建议本身是对的，但题面要求转人工。  
这属于业务规则没定清楚，不能直接判 Agent 错。

## 二、题面/期望问题

### 1. 催件题要求 confirm

有 5 条：

```
h150-a-s035 / s037
h150-b-s034 / s035
```

期望：

```json
{"type": "confirm", "action": "urge"}
```

但催件不是写操作，设计上就是直接创建 `URGE`，不需要确认。  
Agent 实际已经调了 `urge_logistics`，回复“已提交催件”，这是**对的**，是题面期望写错。

### 2. 多候选题要求直接 confirm

14 条 confirm 失败带候选，例如：

```
h150-b-s023
输入：杯子要退 先给我个退货地址
实际：Agent 列出 CS2024250 / 4249 / 4248，让用户选
期望：直接 confirm CS2024248
```

用户只说“杯子”，没有日期/订单号；Agent 不猜是对的。  
题面要求直接 confirm 唯一订单，属于期望过硬。

### 3. tool 列表过严

例：

```
h150-a-s011
期望：query_order + query_logistics
实际：find_my_orders
```

Agent 先用 `find_my_orders` 按日期找候选，这是合理路径；题面要求直接 query。  
这类失败不代表行为错，代表期望工具集写死了。

## 三、需要 judge 才能判

### handoff 11 条

其中 7 条 Agent 给了政策答案：

- 超期退货
- 定制超期
- 赠品
- 物流超期

Agent 回答“不能退/需转保修/需人工”，题面要求 `handoff`。  
这要看业务规则：

- 是“必须挂起转人工”，还是“解释清楚即可”？
- 如果没有明确规则，结构检查会误判。

### 安全 3 条

Agent 给了停用建议，但没 handoff。  
安全场景是否必须 handoff，也需要产品定规则。

## 四、确认脚本为什么失败

11 条脚本失败，主要是：

1. 第一轮多候选，Agent 让选单（合理）
2. 第二轮用户用日期/描述回答，Agent 没解析成订单
3. 第三轮没有 interrupt，脚本判失败

例：

```
h150-a-c010
第 1 轮：列出 3231/3232/3230
第 2 轮：“10月28号是那个”
第 3 轮：Agent 说查不到
```

这不是执行器问题，执行器已经能跑三步。  
是 **Agent 的选单上下文没有接住日期回答**。

## 五、当前不能下的结论

- 不能说“系统准确率 60%”
- 不能说“规则基线一定更高/更低”
- 不能说“handoff 一定该做”
- 不能按这份结果改 held-out 题

## 六、下一步

### 先修 Agent 真错

1. **明确订单 + 明确动作 → 必须弹确认**
   - 加确定性校验：如果已有 explicit order + write intent，模型没调写工具，强制重试一次
2. **选单后锁定**
   - 用户用日期/商品回答候选时，解析到候选并写 active_order
3. **相对时间**
   - “昨天到”按 deliveredAt 解析，不能取成今天
4. **安全场景规则**
   - 鼓包/发烫是否必须 handoff，由产品定

### 再修题集 v2

- 5 条 `confirm + urge` 改为 `tool`
- 14 条多候选 confirm 改为 `clarify` 或多步脚本
- handoff 题明确“必须挂起”还是“解释即可”
- tool 期望改成“允许集合”，不是唯一路径

### 最后才做 judge

- 用现有 150 条 v1 做 judge，不改题
- judge 只判语义，不重判结构
- 人工 30 条校准

# LLM judge 第二轨基线（2026-11-13）

## 为什么要第二轨

第一轨是子串匹配（`must_contain`）：便宜、确定，但只能证明「事实要点出现过」，不能证明「用户的问题被解决了」。
第二轨用 LLM 判断是否解决，专门抓「要点齐全但答非所问」。

## 命令

```bash
# 需要模型 Key；会产生真实调用
uv run python -m eval.run_eval --cases eval/business_cases.jsonl --limit 20 --judge
```

- judge 模型：`settings.model_reasoning`（本次为 `deepseek-chat`）
- `--judge-limit N` 可抽样；没有 Key 或调用失败时标记 `judge_skipped`，不会伪装成 0 分

## 结果（业务集前 20 条，2026-11-13）

| 指标 | 值 |
|---|---|
| 用例 | 20 |
| 子串回复符合率（第一轨） | **85.0%** |
| LLM judge 解决率（第二轨） | **60.0%（12/20）** |
| judge 模型 | deepseek-chat |

**两轨差 25 个百分点**，差额主要来自「回复里有事实、但没真正解决」：

| 类型 | 例子 | judge 理由 |
|---|---|---|
| 要求补充信息，没查 | b05「我想看看我的订单」 | 仅要求提供订单号，未实际查询 |
| 身份核验打断 | b08「帮我看下订单 CS2024001 买了什么」 | 仅要求手机尾号，事实要点缺失 |
| 查不到就结束 | b06「CS2024009 这个订单怎么回事」 | 未查到记录，仅让核对后重试 |
| 未执行动作 | b17「帮我催一下 CS2024002」 | 以不符合催件条件拒绝，未实际催件 |
| 关键词齐全但没答全 | b01「帮我查一下订单 CS2024001」 | 要求补充身份信息，未直接解决 |

## 诚实边界

1. **judge 是模型判模型**，不是人工标注；没有做人工一致性校验（这是校招项目的取舍，面试可主动说明）
2. 样本只有 20 条，不能当总体解决率；扩大样本成本线性增长
3. 失败判定里有一部分是**产品策略**而非缺陷：例如「催件需满足条件」「查询需核验身份」是设计选择，judge 按「是否解决」一律判未解决；调优前应先明确判定口径
4. judge 走 `fast` 之外的 `reasoning` 模型：`fast` 任务可能配置成另一个供应商（本次 Qwen Key 不可用，会 401）
5. 报告里同时保留两轨，不允许只报高的那一轨
